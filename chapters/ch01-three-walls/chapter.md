# 第 1 章　端侧 LLM 与 LiteRT-LM：三类物理约束与同类运行时对照

> 本章先讲清 LiteRT-LM 是什么、与 LiteRT 如何分工，再把内存容量、内存带宽、功耗与异构后端三类约束逐一量化：算一份内存预算，在明确假设下估算 batch=1、稠密模型 decode 的带宽侧吞吐上限，并说明峰值为何未必能持续。这些结果是分析基线，不是具体设备的性能承诺。

## 1.1　LiteRT-LM 是什么：与 LiteRT 的分工

LiteRT-LM 是一个在手机、手表和浏览器等受限设备上运行 LLM 的推理运行时。进入约束分析之前，先回答一个问题：它与 LiteRT 是什么关系。1.2 节说明端侧部署的动机，1.3 至 1.5 节量化三类物理约束，1.6 节对照同类运行时。后续章节讨论实现时，会反复引用这一节建立的软件栈分层。

Google 官方将 LiteRT‑LM 定义为“使用 LiteRT 运行 LLM 的编排层”。[^ch01-litertlm-overview] LiteRT‑LM 处理 LLM 特有的模型容器、tokenizer、提示模板和会话状态。它还组织 prefill/decode 循环与采样，处理约束解码、工具调用和多模态输入。LiteRT 则负责通用模型的加载、编译、张量缓冲和执行，把计算分派给 CPU、GPU 或 NPU 对应的实现。本书把每一条这样的执行路径称为后端（backend），它包括处理器本身，也包括驱动它的 kernel、后端委托与厂商运行时。一部手机是一台设备，上面通常同时有 CPU、GPU、NPU 几个可选后端；选后端选的是执行路径，不是换设备。LiteRT 的 `CompiledModel` API 通过编译选项选择后端，然后提供同步或异步的模型调用。[^ch01-litert-overview]

二者不是并列关系。LiteRT‑LM 调用 LiteRT，使用者通常不直接操作 `CompiledModel`；反过来，只使用 LiteRT 也不会自动获得对话历史、停止条件或工具调用——这些属于 LLM 的上层语义。

| 层级           | 主要职责                                                     |
| :------------- | :----------------------------------------------------------- |
| 应用与语言 API | 业务输入、生命周期、权限与产品交互                           |
| LiteRT‑LM      | 读取 `.litertlm`，创建 Engine/Session，组织输入、prefill、decode、采样和输出；将 backend 配置传递给执行器 |
| LiteRT         | 创建 `Environment`、`Model`、`CompiledModel` 与 `TensorBuffer`，按选项编译并执行模型 signature |
| 平台后端       | CPU/GPU/NPU 的 kernel、后端委托、厂商运行时与驱动            |

> 表 1-1　LiteRT‑LM 管理 LLM 生成过程，LiteRT 管理模型图和张量的设备执行；平台后端决定算子在哪块硬件上执行。

signature 是模型暴露的具名调用入口，规定了该入口的输入输出张量。张量维度可以是静态的，也可以包含运行时确定的动态维度；具名入口并不要求输入长度固定。本书基准模型采用静态入口，包括 `prefill_128`、`prefill_1024`、`decode` 和 `verify`。其中两种 prefill 入口的输入长度分别为 128 和 1024，运行时按输入长度选择并分块。第 4 章说明固定长度带来的填充，以及动态形状路径的处理方式。

这条调用链在代码里如下。`Engine` 初始化时先取得 LiteRT 的 `Environment`，再创建专用执行器；执行器从 `.litertlm` 模型包中读取 prefill/decode 子模型，并调用 `CompiledModel::Create` 完成后端编译。这里的编译发生在设备上：`.litertlm` 存放的子模型是离线转换得到的可移植计算图与权重，GPU 的 kernel 程序要等首次创建时在设备上编译，编译产物可写入程序缓存复用；NPU 路径另有绑定芯片代际的预编译产物。

运行阶段，LiteRT‑LM 负责准备 token、position、attention mask 与 KV cache buffer。在 CPU/GPU 的通用 compiled-model 路径中，prefill 按同步设置调用 `Run` 或 `RunAsync`，decode 通过 `RunAsync` 提交。第 4 章说明 prefill 的等待条件与 Metal 同步限制；第 8 章区分通用执行器、NPU 专用执行器与 ARTISAN 路径。

## 1.2　为什么要在端侧部署

以离线邮件改写为例：模型和输入都在手机上。用户需要等待片刻才能看到第一个 token，之后以每秒几个到几十个 token 的速度生成。模型结构可以完全一致，但手机的内存、算力和功耗预算远不及服务器，响应速度可能差很多。

选择端侧部署，通常出于几方面考虑：

- 数据边界：模型、输入与后处理都在设备上执行时，业务数据不必发送给推理服务。
- 网络时延：本地执行省去了推理请求的网络往返。
- 服务成本：推理在用户设备上执行，相应的计算与能耗不再由服务端承担。
- 离线可用性：模型文件、运行时和所需数据都在本地时，推理不依赖网络连接。

需求成立之后，还要判断设备是否具备运行条件。服务器可以通过增加加速卡或分布式执行扩展资源；移动设备的内存容量、内存通道和散热条件在运行时基本固定。因此端侧 LLM 同时面临三类约束：内存容量、内存带宽，以及功耗与异构后端。

本章使用便于验算的示例参数，每处假设都会标出。三类约束各有一处估算与实测的差距：模型文件大小不等于进程峰值内存，硬件标称带宽不等于有效带宽，DRAM 访问能耗也只是整机功耗的一个组成部分。附录 D 给出本书的实测数据，第 6 至第 9 章再结合 LiteRT-LM 的实现分析这些差异。

## 1.3　第一类约束：内存容量

模型能否运行，取决于推理进程（集成并运行 LiteRT-LM 的宿主进程，例如应用自身的进程）的可用内存能否容纳权重、KV cache、激活张量、后端工作区（存放算子中间结果的暂存内存）和运行时开销。设备的物理内存还要供操作系统与其他进程使用，不能全部算进模型预算。本节按权重、KV cache、激活与工作区逐项估算，最后把可估算的部分合成一份预算示例。

### 1.3.1　权重的理想大小与量化

权重大小的理想值等于参数量乘以每参数位宽；这个口径只计权重数值本身，不含量化附加数据与文件元数据。FP32 每参数 4 字节，FP16 每参数 2 字节，INT8 每参数 1 字节。低比特量化可以减小权重大小，但不同端侧模型采用的格式不一定相同。本章以 INT4 为例，每个参数按 4 bit（0.5 字节）计算：

$$ 4 \times 10^{9} \text{ 参数} \times 0.5 \text{ 字节/参数} = 2 \times 10^{9} \text{ 字节} \approx 1.86 \text{ GiB} $$

其中 1 GiB = \\(2^{30}\\) 字节，这里的 1.86 GiB 只是 INT4 权重大小的理想值。量化把浮点权重映射成整数保存，还原时按反量化公式 \\(x \approx s \times (q - z)\\) 计算：\\(q\\) 是保存的整数，\\(s\\) 是 scale（整数每差 1 对应的实数步长），\\(z\\) 是 zero point（实数 0 对应的整数）。直观地说，若一组权重的 scale 是 0.25，整数 4 反量化后就代表 1.0；对称量化下 \\(z=0\\)，可以省略。scale 不必每个权重存一份，常见做法是按整层、按通道或按权重分组（如每 32 或 64 个一组）共享；但无论怎么共享，scale 都要写进模型文件，占用真实字节。第 7 章的 2B 案例会按分组算出这个数值。文件里除了权重和这些量化附加数据，还有对齐填充、元数据，也可能包含其他模型段。所以，参数量乘位宽不能直接换算出文件大小。

### 1.3.2　权重的驻留口径与工作集

模型文件如何进入进程内存，决定这些字节以什么口径占用。LiteRT-LM 可以从只读的内存映射文件创建模型。`ModelResources` 的注释说明，内存映射模型在实际使用时才分配物理页。它还为外部权重（不内嵌在模型图里、单独存放在权重段、不应被 mmap 的权重数据）保留独立的文件接口。

mmap 建立的只是虚拟地址映射：一方面，1.86 GiB 不保证始终全部驻留物理内存；另一方面，推理时真正访问到的权重页面仍要占用物理内存，映射本身省不掉这部分。而端侧推理通常会反复读取几乎全部权重，原因在执行方式上。batch（批大小）指一次前向计算并行处理的序列数：服务端把多个用户的请求拼成一批同时前向，权重读入一次，这一批里的所有请求共用，读取成本由它们分摊；端侧通常只有一个用户的一个请求在生成，同一时刻只有一条序列可算，batch=1。batch=1 的稠密 decode（稠密指所有参数每步都参与计算，区别于 MoE 等稀疏激活架构）每一步只生成一个新 token，而模型远大于片上缓存（CPU/GPU 芯片内的多级高速缓存，容量最大的一级通常也只有几 MiB 到几十 MiB），这一步用到的权重基本都要从主存读入；每一步都如此，工作集就接近全部权重。

工作集之外，后端自身还会增加占用。为了让硬件高效访问，权重可能被再复制或重排一份；设备上编译出的 kernel 程序要驻留内存；中间计算还需要工作区，即后端预先分配的一块暂存内存，矩阵乘法、注意力这类算子把中间结果放在里面，多个算子轮流复用同一块。所以，模型文件大小、虚拟映射大小（mmap 占用的地址空间）、RSS（实际驻留物理内存的部分）和进程峰值内存是四个口径不同的数字；判断内存预算是否满足，要以实际部署所选的后端（下文称目标后端）上的运行时实测为准。

### 1.3.3　KV cache 的理论大小与预留宽度

权重的理想值只由模型和量化格式决定，算一次就不再变。内存预算的第二大项 KV cache 不同，它随上下文长度增长，上下文足够长时甚至会超过权重。自回归注意力会复用历史 token 的 Key 和 Value，KV cache 保存这些张量，避免每一步重新计算全部历史 K/V。忽略填充、量化元数据和多缓冲时，每个会话的 KV cache 理论大小（每个已缓存 token 恰好保存一份 K 和 V 所需的字节数）可写成

$$ \text{KV cache 字节} = 2 \times L \times n_{kv} \times d_{head} \times S \times b $$

其中 2 表示 K、V 两份张量；\\(L\\) 是层数，\\(n_{kv}\\) 是 KV 头数，\\(d_{head}\\) 是每头维度；\\(S\\) 是已缓存 token 数，\\(b\\) 是每个元素的字节数。取一组示意参数：\\(L=32\\)、\\(n_{kv}=8\\)、\\(d_{head}=128\\)，KV 采用 FP16（\\(b=2\\)）。于是每缓存一个 token，需要保存的 K/V 字节数为

$$ 2 \times 32 \times 8 \times 128 \times 2 = 131072 \text{ 字节} = 128 \text{ KiB} $$

上下文为 4096 个 token 时，理论大小约为

$$ 128 \text{ KiB} \times 4096 = 0.5 \text{ GiB} $$

按同一组参数，上下文增至 8192 个 token，理论大小增至 1 GiB。真实模型的层数、GQA（grouped-query attention，分组查询注意力，多个 query 头共享一组 KV 头）配置和数据类型各不相同，这里的 128 KiB/token 只对本组示意参数成立，不能外推到其他模型。

上面的理论大小是理想口径：恰好为已缓存的 \\(S\\) 个 token 各分配一份数据，不含填充、量化元数据和多缓冲，而实际分配通常不满足这三条假设。后端往往按预留宽度分配（预先为最大 token 数分配好槽位，而不是随 \\(S\\) 逐 token 增长）：例如预留 4096 个 token 的槽位而只缓存了 1000 个时，buffer 仍按 4096 准备，占用约是理论大小的 4 倍。不支持原地更新的后端还要准备输入、输出两套 KV buffer，容量接近理论大小的两倍，代价见 1.4 节。张量对齐与后端工作区也会叠加额外字节。因此，理论大小的用途是估算下限和横向比较：它是模型结构决定的每 token 最少字节数，便于在同一口径下比较不同模型；实际占用是否超出内存预算，仍以目标后端在目标上下文下的实测为准。

预留宽度如何增长，由运行时参数控制。LiteRT-LM 对动态导出的 CPU 模型提供增量扩容参数：decode 时按 `CpuConfig::kv_increment_size` 增加 KV cache 大小，默认值为 16。较小的增量会增加 `Resize` 的调用次数，较大的增量则可能提前预留更多空间。重分配次数、内存碎片和峰值占用仍取决于具体执行后端的实现，需要实际测量。

### 1.3.4　激活、工作区与内存预算示例

权重和 KV cache 可以按模型结构估算，激活与工作区不行。仅凭层数 \\(L\\) 和模型宽度 \\(d_{model}\\) 算不出激活的内存峰值：FFN（前馈网络）的中间维度、算子调度和张量生命周期都会影响它；buffer 复用、数据类型与后端工作区（scratch buffer）的分配方式也会改变结果。batch=1 的 decode 每次只处理一个新 token，激活张量通常小于长序列 prefill。未实测时，不应给激活指定固定数值，也不应忽略后端工作区。

降低激活内存峰值的一种手段是把 prompt 分块处理：动态导出的模型可以用 `CpuConfig::prefill_chunk_size` 控制每次 prefill 的 token 数，默认值 -1 表示不分块。例如 2048-token 的 prompt 取 chunk=512 时，一次 prefill 变成至少四次调用，每次最多处理 512 个 token，与序列长度相关的中间张量可能因此缩小。固定工作区、buffer 复用与后端调度会改变比例，不能据此认定峰值恰好降到四分之一。分块变多次调用后，首 token 时延（TTFT，time-to-first-token）会升高还是降低、变化多大，同样需要在目标设备上实测。

现在把权重和 KV cache 合成一份预算示例：假定设备物理内存 8 GiB，操作系统和其他进程合计占用 4 GiB，推理进程还剩 4 GiB 可用。其中，4B 模型的理想 INT4 权重占 1.86 GiB，按本节示意参数计算的 4096-token KV cache 占 0.5 GiB，两项合计 2.36 GiB，剩余约 1.64 GiB。这份余量还要容纳量化附加数据、激活、后端工作区、权重复制或重排、运行时对象与内存碎片。所以，仅凭权重和 KV cache 两项，不能判定模型一定能运行。

在相同假设下，理想 INT8 权重约为 3.73 GiB，加上 0.5 GiB KV cache 后共约 4.23 GiB，尚未计入工作区就已超过 4 GiB。若仍采用 128 KiB/token 的示意参数，32K 上下文的 KV cache 为 4 GiB，与 INT4 权重合计约 5.86 GiB。这组对比给出的是方向性结论：位宽越低、上下文越短，内存预算越容易满足；它不保证 INT4 在任何设备上都可用。

多大的模型能放进内存，也可用相同方法判断：70B 权重按理想 INT4 口径计算约为 32.6 GiB，尚未计入量化附加数据、KV cache 和工作区，已远超上述题设中 4 GiB 的进程预算。一台设备能运行多大的模型，取决于可用内存、模型结构、量化格式与后端实现；本章取 4B 只是示例取值，不是端侧模型的规模上限。

手机实测还要区分进程内存读数与后端的全部内存占用。附录 D 第十四节在 HONOR MEP-AN00 上以 OpenCL 后端运行 Gemma 4 E4B，分阶段记录了加载、prefill、decode 与释放时的进程内存：模型文件约 3.408 GiB，而进程 RSS 只覆盖该进程可观察的驻留页，读数小于文件体积，不能据此认定模型的全部工作内存也小于文件体积。判断能否部署，需要同时确认读数覆盖了哪些分配，以及哪些设备侧内存仍未计入。

权重大小与 KV cache 的估算，在工程实现里各有一章展开。KV cache 的预留与缓冲策略见第 6 章，权重的量化格式与加载路径见第 7 章。

## 1.4　第二类约束：内存带宽

LLM 生成分为两个阶段：prefill 一次性处理完整的提示词，建立生成所需的上下文；decode 在此基础上逐个生成输出 token。两个阶段的计算特征不同：prefill 同时处理许多输入 token，一次读入的权重服务于所有这些 token，算术强度（每访问一字节数据对应的运算次数）通常高于 decode；decode 按自回归顺序生成，第 \\(N+1\\) 步依赖第 \\(N\\) 步的结果，单个会话不能任意并行这些步骤。不过，具体工作点的算术强度仍会受内存访问模式、输入的填充比例和 kernel 效率影响；填充从何而来，见第 4 章的固定 signature 分块机制。

先把估算范围限定在 batch=1 的稠密 Transformer。对这类模型，1.3 节的内存事实可以直接换算成带宽需求：GiB 级权重无法放入 MiB 级片上缓存，每个 decode step 都要从主存重读大部分权重，相当于每生成一个 token 就读取一次接近权重大小的数据。MoE、结构化稀疏、权重常驻片上缓存或分层卸载不满足这条前提，本节的估算不适用于这些情形。

Roofline 模型给出这类估算的标准框架：吞吐上限等于带宽上限与算力上限中的较小者，完整介绍见第 2 章。设每个 token 的数据访问量为 \\(D\\) 字节，计算量为 \\(F\\) 次运算；工作负载可用的有效带宽记为 \\(B_{\mathrm{eff}}\\)，对应数据类型的有效计算吞吐记为 \\(P_{\mathrm{eff}}\\)。则

$$ R \leq \min\left(\frac{B_{\mathrm{eff}}}{D},\frac{P_{\mathrm{eff}}}{F}\right) $$

其中 \\(R\\) 是生成吞吐，单位 tokens/s；\\(B_{\mathrm{eff}}/D\\) 是带宽侧上限，\\(P_{\mathrm{eff}}/F\\) 是算力侧上限。一个具体负载在一套具体硬件上运行，这四个量就都有了确定取值，这样的组合称为一个工作点。若某个工作点的带宽侧上限更低，它就受带宽约束：提高算力吞吐不会改变上限，只有提高有效带宽或减少每 token 的数据访问量才能提高这个上限。

数值示例的题设如下。模型取 4B 的理想 INT4 稠密权重；上下文较短，每步随之读取的 KV cache 只有几十 MiB，相对 1.86 GiB 的权重可以先忽略，上下文变长的情形在本节稍后讨论。再假定低比特 kernel 足够有效：量化解包（计算前把 INT4 权重还原成可运算数值）、各步之间的同步等待和采样（从每步输出中选出下一个 token）都没有先成为瓶颈，否则上限就不由带宽决定。该工作负载可用的有效内存带宽假定为 \\(B_{\mathrm{eff}}=50\\) GB/s；这只是便于验算的题设，不对应某款 SoC 的规格或实测值。

短上下文时取 \\(D \approx 2\times10^9\\) 字节，即权重大小。代入后，带宽侧上限为

$$ R_{\mathrm{bw}}=\frac{50 \times 10^{9}\ \text{字节/s}}{2 \times 10^{9}\ \text{字节/token}}=25\ \text{tokens/s} $$

25 tokens/s 是上述假设下的上限。若算力侧上限反而更低，或量化解包、同步与采样引入额外开销，实际吞吐只会更低，不会更高。这也说明单纯提高算力未必有用：芯片标称的 TOPS（每秒万亿次运算，算力吞吐的常用指标）再高，也改变不了带宽侧的 \\(B_{\mathrm{eff}}/D\\)；只有当工作点尚未受带宽约束、瓶颈还在计算或其他开销上时，提高算力才可能带来实测吞吐的提升。

现在加入先前忽略的 KV cache。普通的全上下文注意力里，每个新 token 都要与全部已缓存 token 计算注意力，先按每个 decode step 从 DRAM 把已缓存 K/V 完整读取一遍计算。按 1.3 节的参数，4096-token 的 KV cache 共 0.5 GiB，这部分读取直接计入每步的数据访问量；写入侧只有新 token 自己的那份 K/V（128 KiB，为读取量的 1/4096），可以忽略。于是分母 \\(D\\) 从 1.86 GiB 增至 2.36 GiB：

$$ \frac{50 \times 10^{9}\ \text{字节/s}}{2.36 \times 2^{30}\ \text{字节/token}} \approx 19.7\ \text{tokens/s} $$

19.7 tokens/s 同样只是上限估算：缓存命中、预留槽位是否被实际读取、注意力 kernel 的实现和 KV 数据类型，都会改变真实的 DRAM 流量。不过，上下文越长、decode 越慢这个方向可以用实测对照。附录 D 的 Gemma 4 E4B 基准中，上下文从 256 增至 4096 时，CPU decode 从 24.8 降至 20.7 tokens/s，约下降 17%，与 KV 读写量和注意力工作量随上下文增长的分析方向一致；但不能仅凭端到端吞吐就把降幅全部归于 KV cache。还要注意口径：该基准的设备、模型与后端都与本节题设不同，实测值验证不了 25 tokens/s 这个点值，只能检验同一套分析方法。

题设还有一个没有回答的问题：50 GB/s 这样的有效带宽的来源。它不是硬件标称峰值乘一个固定比例。访问模式、缓存行为与共享内存总线上的其他流量都会改变推理实际获得的 \\(B_{\mathrm{eff}}\\)，解包计算和同步也会占用时间。若直接用标称峰值代入公式，得到的只是更宽松的上界。目标工作负载的有效带宽，应通过硬件计数器或可比的基准实测获得。

1.3 节提到的双缓冲代价在这里说明。支持原地更新的后端让输入、输出指向同一组 KV buffer；不支持时，LiteRT-LM 返回两组 buffer 并在调用间交换，张量形状相同时，KV buffer 的占用接近单组的两倍。翻倍的只是 KV buffer 这一项；权重、激活等项不受影响，整个进程的内存占用不会因此翻倍。

硬件峰值带宽由设备决定，软件能改变的只有两件事：提高有效带宽的利用率，或减少每步访问的字节数。prefill 因权重复用通常受算力约束，batch=1 的稠密 decode 则通常受带宽约束，二者都要用实际工作点确认。减少每步字节数正是后文两项技术的出发点：量化压缩权重本身（见第 7 章），投机解码让一次权重读取确认多个 token（见第 9 章）；但能否变成实际的吞吐提升，还取决于 kernel 实现、草稿 token 被接受的比例和额外计算开销，不能只凭方法名称判断。

## 1.5　第三类约束：功耗与异构后端

1.4 节算的是速度上限，第三类约束决定这个速度能维持多久：峰值吞吐不等于持续吞吐。移动设备依赖电池供电，持续高负载会使芯片温度升高，可能触发系统的功耗或温控策略。评估端侧推理时，需要记录稳态吞吐、功率和温度随时间的变化，而不能只报告短时峰值。

附录 D 第十四节记录了一台带壳 HONOR MEP-AN00 的持续运行：Gemma 4 E4B 使用 GPU OpenCL，固定 77-token 输入与 4096-token 上限，关闭 MTP，约 15 分钟内完成 44 次请求。后几轮的吞吐低于开始的几轮，结束时机身表面（skin）温度传感器的读数仍在上升。这个案例补充了持续吞吐与温度的观察，但没有可靠的功率数据，验证不了下面能耗公式中的示意取值。案例分析见 8.8 节，具体曲线与采集限制见附录 D 第十四节。

功耗侧同样可以先做一个可验算的估算。设每个 token 的 DRAM 流量为 \\(D\\) 字节，每访问一字节 DRAM 的能耗为 \\(e_{\mathrm{byte}}\\)，则数据访问部分的能量近似为

$$ E_{\mathrm{mem/token}} \approx D \times e_{\mathrm{byte}} $$

\\(e_{\mathrm{byte}}\\) 随制造工艺、内存类型、访问局部性、功耗状态和测量口径变化，没有跨设备通用的常数，下面只演示代入方法。这里先分清口径：能耗资料常按每比特给出 DRAM 访问能耗，Horowitz 给出的 640 pJ / 32 位访问即 20 pJ/bit，折合每字节 160 pJ。[^ch01-horowitz] 本节按每字节代入，取 \\(e_{\mathrm{byte}}=20\\) pJ/byte（1 pJ = \\(10^{-12}\\) J）；这个取值与上一句的 20 pJ/bit 数字相同、量纲不同，两者不可互引，换用其他来源时须先确认它按比特还是按字节给出。每 token 的 DRAM 流量仍取 1.4 节的 \\(2\times10^9\\) 字节，则

$$ 2 \times 10^{9}\ \text{字节} \times 20 \times 10^{-12}\ \text{J/字节} = 0.04\ \text{J/token} $$

20 pJ/byte 是按每字节计的示意取值，不是本书设备的实测值，也不存在跨设备通用的常数；若改用上一段的每比特口径（160 pJ/byte），这里的结果将是现在的 8 倍。算出的 0.04 J/token 也只覆盖 DRAM 访问一项，不含算术运算、量化解包、显示、操作系统、无线电和电源转换，不能据此推算手机续航或可生成的 token 总数。整机能耗要在目标设备上实测。

减少 DRAM 流量能同时降低带宽占用与访问能耗，但只有当这两项在总成本中占主要部分时，收益才接近线性。软件侧另有一组影响功耗的可调参数：线程数、核心绑定和异步调度都会改变吞吐、功率与温度，取值应依据持续负载实验确定。

核心绑定在 LiteRT-LM 里有一个真实实例。Android 路径的亲和性工具读取 SoC 厂商与型号属性，按型号查预置的中核、大核编号表：Google Tensor G4 返回 `{4,5,6,7}`，G5/G6 返回 `{2,3,4,5,6,7}`；`SetCpuAffinity` 随后调用 `sched_setaffinity` 完成绑定。源码注释只说明该选择用于性能优化，没有配套的能耗或温控测量，不能据此断言这组编号在所有负载下最省电。

功耗之外，异构后端还有可用性问题：CPU 通用性最强；GPU 与 NPU 的可用算子、驱动和内存路径随设备而变；专用加速器只在受支持的计算图上才可能体现能效优势。所以，离开具体的模型、量化格式、后端委托（delegate）和设备实测，不能给 CPU、GPU、NPU 排出固定的优劣次序。

后端的差别不止于快慢与能耗。不同后端的算子实现和浮点路径可能产生数值差异；在自回归生成中，早期差异会影响后续 token。但这不意味着所有输出差异都可以归因于数值路径：异常结果仍需用容差测试、逐层对比和已知 issue 排查。第 8 章结合 `LiteRT-LM#2281` 分析一个真实的后端输出差异案例。[^ch01-issue-2281]

这些可选后端在代码里对应 `Backend` 枚举：通用项有 `CPU`、`GPU`、`NPU` 与 `UNSPECIFIED`，另有 `CPU_ARTISAN`、`GPU_ARTISAN`、`GOOGLE_TENSOR_ARTISAN` 三项，源码把前两个 Artisan 标为手写算子路径（hand-written path），Google Tensor 项标为 Emission Graph。枚举只能证明运行时暴露了多条可选执行路径，证明不了哪条更快或更省电；各路径的实现与测量见第 8 章。

三类约束合起来是一条配置评估规则：内存预算、Roofline 工作点、持续功耗和后端支持必须同时检查，任何一项不满足，配置就不可行。一项优化的代价也常常出现在另一类约束上：量化减小权重大小，但可能增加解包计算或缩小后端支持范围。投机解码用一次前向确认多个 token，但草拟和验证本身有额外成本。`LiteRT-LM#2227` 就记录了特定 GPU 条件下的负收益。[^ch01-issue-2227]

## 小结

1.1 节建立的软件栈分层在后续章节反复用到：LiteRT‑LM 组织 LLM 生成语义，LiteRT 负责模型编译与张量执行，平台后端决定算子在哪块硬件上执行。内存预算必须同时覆盖权重、KV cache、激活、后端工作区和运行时开销。低比特量化是减小权重大小的常用选择，但是否可运行仍要以目标后端的峰值内存为准。

在 batch=1、稠密模型、权重远大于片上缓存且 kernel 有效的条件下，decode 通常主要受内存带宽约束。本章以 4B 理想 INT4 权重和 50 GB/s 有效带宽为题设，算得的 25 tokens/s 是带宽侧上限；完整的 Roofline 上限还要与算力侧比较，真实上下文还要把 KV cache 与其他流量加进分母。

功耗与后端决定峰值能否持续。20 pJ/byte 只是示意假设，不能推导整机续航；CPU、GPU 与 NPU 的性能和能效也必须针对模型与设备测量。

## 练习与自查

1. 内存预算复算。一台 12 GiB 手机，题设假定操作系统与其他应用合计占用 5 GiB。按 KV cache 每 token 128 KiB 计算。求 7B 模型的理想 INT4 权重与 8K 上下文 KV cache 的字节数。仅凭这两项能否判定可运行？上下文增至 32K 时呢？
2. 带宽侧上限复算。一款 SoC 使用 LPDDR5X-9600 与 64 bit 总线。先由数据率与总线宽度推导理论峰值带宽，再估算 INT8 4B 稠密模型的带宽侧 decode 上限。说明为什么它不是持续性能承诺。
3. 能耗假设变体。题设明确假定 \\(e_{\mathrm{byte}}=20\\) pJ/byte，按每字节计，不与 20 pJ/bit 混用。若 INT4 2B 模型每 token 产生约 1 GB DRAM 流量，计算 DRAM 访问能耗。再计算把 15 Wh 全部用于这一项时的算术上界，并说明它为什么不代表设备续航。
4. Roofline 判断。解释为什么 batch=1 的稠密模型通常表现为 prefill 算术强度较高、decode 算术强度较低。再列出一个会破坏该简化判断的条件。
5. 条件判断。某 decode 工作点已确认受带宽约束。若芯片计算吞吐翻倍而有效内存带宽不变，带宽侧上限是否变化？若尚未确认瓶颈，为什么不能直接作答？
6. 层级判断。某次部署中，模型加载与编译成功，首次调用 `Run` 时返回硬件驱动错误。这个错误位于软件栈的哪一层？排查时应从哪个运行时开始看？
