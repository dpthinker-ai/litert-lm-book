# 尾声 · 出发

> 拆完了，该上手了。这篇尾声不引新代码，只做三件事：指几条把它用起来的路，说说怎么参与进去，再往前望一眼。

从第 1 章那三堵墙，到一个 token 走完它的一生，再到凿墙的各种手艺、多模态、工具调用、六种语言的绑定——LiteRT-LM 这台端侧推理机器，我们从里到外拆了一遍。拆的目的从来不是拆本身，是为了看懂之后能动手。

## 三条上手的路

你不必从源码编译起步。按你的场景，挑一条最短的：

- **先跑起来、做实验**：用 Python CLI（第 2 章那个 `litert-lm`）。一条命令装好、一条命令跑模型，改参数看变化最快。想把模型接进 Python 程序，用它的 Python SDK。
- **做 Android App**：用 Kotlin SDK（第 11 章）。它是预编译的，不用碰 Bazel；`Engine`/`Session`/`Conversation` 的用法就是本书前几章那套接口的 Kotlin 镜像。iOS/macOS 同理，用 Swift 包——记得第 11 章那个 `close()` 的教训，会话用完主动释放。
- **做网页**：用 Web SDK，核心编成 WASM 在浏览器里跑，纯前端、不联网。

三条路的共同点：**都不需要你懂 C++ 核心**。但读完这本书，当某一条路出了问题（某个后端跑不动、某段生成变慢、某个模型加载失败），你会知道该往哪一层去看。这正是拆解的回报。

## 参与进来

LiteRT-LM 是开源的，它的 issue 列表是一座真实问题的富矿。想参与，先学会分辨：

- 有些 issue 是**硬件深坑**——某块特定 GPU/NPU 上的崩溃、某个 SoC 上的数值异常。它们要对应的设备才能复现，门槛高（本书第 8、9 章引的 `#2281`、`#2227` 就是这类）。
- 有些是**小而清晰的改进**——一个缺失的 API、一处误导的提示、一个能补的边界处理。第 11 章那个 Swift `close()`（`#2589`/`#2613`）就是典型：范围小、有清晰的参照（Kotlin 早有 `AutoCloseable`）、纯增量、低风险。这类适合作为第一个贡献的切入点。

分辨这两类的能力，本身就是这本书想给你的：读懂了机制，你才看得出一个 issue 是"需要一屋子设备"还是"读几个文件就能动手"。（贡献前留意项目的协作约定，比如 Google 系项目通常需要签署 CLA。）

## 往前望一眼

端侧推理这条路，还在快速往前。几个方向值得留意：

- **更激进的量化**。第 7 章讲了 int4。带宽墙的压力会继续把量化往更低比特推，也会催生更聪明的量化方式，在"更小"和"够准"之间找新的平衡点。
- **NPU 的普及**。第 8 章说 NPU 最省电但最封闭。随着端侧 AI 成为标配，NPU 的接口会更成熟、覆盖的算子会更多——第三堵墙里"异构"这一半，天平会慢慢往能效倾斜。
- **从"生成"到"agent"**。第 10 章的工具调用是个起点。当模型能可靠地调函数、看屏幕、连成多步，端侧就不只是"本地的聊天框"，而是一个装在你口袋里、离线也能干活的助手。

这些方向都还没有定论，也正因如此，现在入场不晚。

## 最后

这本书用 LiteRT-LM 当解剖标本，讲的其实是一门更普遍的手艺：**如何在物理约束的窄缝里，把一件"看起来不可能"的事做成、做稳、做快。** 三堵墙不会消失，但凿墙的手艺会一代代变精。你手里现在有了一把尺子、一张地图，和一整套被真实代码验证过的做法。

接下来，该你出发了。
