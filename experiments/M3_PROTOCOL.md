# M3：手机内存、持续性能与用户时延实测

状态：E01–E03 已完成采集与汇总，采用 4 组、57 个成功请求。本文件规定采集和验收方法；实测数值以各次运行的原始记录与汇总为准。

## 开始前的检查

在书稿仓库执行 `python3 experiments/m3_preflight.py`。脚本只读取设备信息，不启动推理、不安装程序、不改变设置。多台设备连接时必须以 `--serial` 指定目标。输出保存到新的日期目录；指定的 `--out` 已存在时拒绝覆盖。

预检保存每条命令的参数、时间、退出状态、标准输出和错误输出。设备未连接、未授权或离线时停止；模型哈希不符也不能继续。`inventory_collected` 仅表示清单已采集，仍须核对二进制与动态库的构建来源，并验证完整生成及正常停止。源码目录位于 v0.13.1，不能单独证明设备上的二进制由该版本构建。

目标先沿用现有 Android 实验目录 `/data/local/tmp/litertlm` 和 Gemma 4 E4B 模型。预期模型 SHA-256 为 `0b2a8980ce155fd97673d8e820b4d29d9c7d99b8fa6806f425d969b145bd52e0`。更换模型须保存新的身份、哈希和条件，并把结果与旧基准分开。

正式运行前还需保存运行时和采集程序的提交、构建命令、编译器/NDK 版本、二进制及加载动态库的哈希。记录手机型号、系统 build fingerprint、RAM、后端与驱动、CPU 线程数、采样参数、最大上下文和输出上限。现有脚本 `android_bench.sh` 会覆盖旧 CSV，本轮不直接运行它。

## 共用负载与运行条件

先在同一台手机、同一模型上试运行 CPU 和 GPU，选择能够完整生成并正常停止的一条路径作为 E01–E03 的共同案例。确定后固定后端、线程、采样和输入；不把不同后端的内存、吞吐和时延拼成同一次部署结果。

使用固定的自然文本，保存原始 UTF-8 输入、实际渲染输入及其哈希。保留完整输出、真实 token 计数和终止原因。常规生成保留停止序列，不为了凑够 token 数继续生成。固定步数 benchmark 如需补测，须另建记录，不与用户时延混算。

记录 USB/电池供电状态、电量、温度、系统热状态、屏幕状态、省电及厂商性能模式、环境温度和散热条件。保持条件一致，不通过模拟电池或温度读数改变系统行为。没有可靠功率计量时保留功率缺口；电池温度不解释为芯片结温，电量变化不换算为推理功率。

## E01：分阶段内存

在同一个进程内记录引擎加载开始/完成、输入处理、prefill 开始/完成、decode 开始/结束、会话释放、引擎释放。释放后的进程需继续存活一段观测时间，以区分对象资源释放与进程退出。

首先验证对实际推理 PID 的内存采集权限。预检中 `/proc/self/smaps_rollup` 的读取只测试 shell 子进程，不能代替这个验证。以 `/proc/<pid>/status` 的 VmRSS、VmHWM 作为可选观测项，能取得时再采集 smaps_rollup 的 PSS、Private、Swap 等。保留原始字段和单位；字段不可读时记为缺失，不能写 0。

试采时以 500 ms 间隔读取轻量进程指标，在阶段边界读取详细内存；记录每次实际采样时刻及耗时。试采后根据扰动调整频率并固定正式参数。离散采样得到的是“观测到的最大值”，可能遗漏短暂峰值。VmHWM 属于进程生命周期高水位，不能分配给每个阶段，也不能通过相减计算某个对象的内存。

同时报告模型文件大小及观测到的进程内存，不把 RSS/PSS 当成全部 GPU/NPU 内存。若设备不能提供设备分配的完整口径，明确保留这一限制。至少对照一次关闭周期采集的相同负载，以检查采集对运行时间的影响。

## E02：持续吞吐与温度

在一个已加载的 Engine 内重复相同请求，每轮创建并释放独立会话，避免上下文不断增长。会话复用策略、缓存设置和输出上限固定。使用设备单调时钟记录每轮开始、prefill 完成、decode 完成和结束原因，同时保留热状态、温度与供电记录。

先做短试运行确认输出和日志，再固定正式时长及重复次数。初始方案为至少 15 分钟连续运行，按每轮实际输出 token 数与 decode 时长统计吞吐，另报告完整请求耗时。这个时长不是热稳定的保证；若结束时仍有趋势变化，明确记为尚未稳定，不据此宣称持续性能已达稳态。

开始前记录停止条件：系统报告严重或更高热状态、推理错误、采集失联或达到预定时长时结束本次运行。达到时长时允许当前请求在已设定的超时内结束；超时请求标为失败。中途停止的记录保留实际时长及原因，不删掉失败轮次。

温度和吞吐同时变化只能说明相关性。若要归因于降频，还需要相应频率、热限制或更细的执行证据；仅凭曲线不能排除缓存、后台负载和计算成本变化。

## E03：调用开始到可见文本

计时必须放在手机进程内，从应用/测试客户端调用开始记录，不能用 Mac 收到 ADB 输出的时刻代替。需实现并验证以下事件：调用开始、输入处理完成、prefill 开始/完成、每次输出回调、首个非空文本片段、结束回调和释放完成。内部阶段若无法观测，记为不可分解，不能从总时间反推。

每个事件保存请求编号、设备单调时间、事件名、回调文本的原始内容和长度。回调片段不等于 token：只能报告首个可见文本片段时延和片段间隔。只有另有逐 token 生成时刻时才报告 ITL。原始日志写入与输出格式化会影响回调开销，试运行中需要检查并说明。

分别测量新进程/首次加载和同进程引擎已加载两类条件。二者不能直接称为磁盘缓存冷/热；只有实际验证并记录缓存条件后才能这样归类。固定输入的重复请求还须记录是否复用会话或前缀状态。

先保存每次运行明细和输出长度，再按可比条件汇总。试运行用于选择重复次数，不以少量样本估计 P99。失败、超时和未输出文本的运行单列，不通过丢弃它们改善时延统计。

## 产物与完成条件

每次正式运行使用新的 `experiments/data/YYYY-MM-DD/` 子目录，包含完整参数与环境信息、输入/输出、设备事件、资源采样、原始标准输出/错误、退出状态和汇总。数值汇总需由这些记录重算；没有测量的字段保持缺失。

E01、E02、E03 均有同设备同模型的有效记录后，才在附录 D 写数据及适用范围，在附录 C 写已验证的复现步骤，再向相关章节补充结论。设备内事件程序 `m3_observe.cc`、运行器 `m3_run.py` 与汇总器 `m3_summarize.py` 已完成 GPU 试运行验证。预检工具只检查清单，不能代替正式采集。

参考方法：Android Developers 的 [ADB 文档](https://developer.android.com/tools/adb)说明连接与设备选择；[dumpsys 文档](https://developer.android.com/tools/dumpsys)说明进程内存观测；[Thermal API 文档](https://developer.android.com/games/optimize/adpf/thermal)说明系统热状态与设备差异。访问日期：2026-09-05。具体试验参数为本书的采集设计，需经目标设备试运行验证。

## 2026-09-05 试运行后的固定配置

目标为 HONOR MEP-AN00、Android 16、SM8750 / Adreno 830，使用上述 E4B 文件，主干后端为 GPU OpenCL。采样接口配置为 TOP_P、top-k=1、top-p=1、temperature=1、seed=42。GPU 采样库已加载成功；TOP_P 在这里指定运行时支持的采样类型，候选数限制为 1。最大上下文 4096，输出上限 512，MTP 关闭，视觉和音频执行器未启用。CPU 配置沿用源码默认的 4 线程，不手动绑定 CPU 核。

本次采用专用 C API 测试客户端。每轮从文件读取同一 prompt，以临时 Conversation 调用模型自身的模板渲染器，再创建独立 Session 分别调用 prefill 和异步 decode。临时 Conversation 在渲染完成后销毁，不将它的会话状态转给测试 Session。输入处理时延包含读取、渲染和这些对象操作。记录的首段文本是 Session 回调交付的首个非空字符串，不包含 Android UI 排版、绘制和显示扫描时间。本负载的试输出为普通正文；完整字符串保留在日志中。这个客户端路径不代表所有应用的 Conversation 集成方式。

benchmark 计数启用，但强制 prefill/decode token 数均为 0，保留自然输入及停止序列。prefill 会等待完成，这也是客户端计时的一部分；不能把这组时延称为未插桩应用时延。API 开始事件在边界 smaps 读取完成后记录，结束事件在读取前记录，因此 API 阶段耗时不含边界读取本身。请求总时延和首段文本时延仍包含请求路径上发生的采集开销。

周期 status 采样固定为 500 ms，smaps 只在阶段边界读取。关闭内存采集的对照仍保留文本回调日志及每约 5 s 一次的热状态采集，不能据此测出全部日志开销。正式持续运行设为引擎加载后至少 900 s，上限 1000 请求，到时允许当前请求结束；每次 decode 超时 180 s，取消等待上限 60 s。先进行 5 请求无内存采集对照，再自然降温 75 s 至系统热状态 1，运行持续实验，最后进行 5 请求无内存采集复查。各次运行启动新进程，进程内复用 Engine，每轮新建 Session。缓存目录复用，不清空文件缓存，不称为磁盘冷启动。

构建使用 NDK r28c、Android API 31、Bazel 7.6.1。客户端链接官方 C API 动态库；启动时以 LD_PRELOAD 将同批 libLiteRt.so 加载到全局符号范围，供预编译 GPU 采样库解析符号。源提交、编译器、库哈希与构建日志归档于 `data/2026-09-05/m3-build-validated/`。CPU 和 GPU 首轮试运行的 greedy 配置不受回退 CPU 采样器支持，另一轮 TOP_K 也失败；这些失败均保留，不参与正式统计。未设置全局符号加载的 TOP_P 试运行成功，但回退到 CPU 采样，亦不参与正式 GPU 统计。

作者报告的现场条件：带日常手机壳，无风扇或散热器，未开启性能模式；室温估计 22–25 °C，未用温度计测量。原始条件记录单列为 `m3-environment-user-report.json`，不将室温估计当作传感器读数。

完成记录：持续组44请求、901.728619604 s，均正常结束，未达到严重热状态；前后各5请求对照也完成。采用目录及排除原因以同日 `M3_RUNS.json` 为准，汇总由 `m3_report.py` 重算。约定的15分钟时长已覆盖升温，结束时skin仍上升，不能宣称热稳态。
