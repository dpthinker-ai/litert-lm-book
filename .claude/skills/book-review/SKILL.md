# 书稿逐章审校与润色

## 审校方法

对目标章节逐段通读，每条句子过三道滤网，发现问题即用 Edit 就地修正：

### 滤网一：通顺

- 句子是否过长（中文单句超过 50 字应拆分）？
- 修饰语是否堆叠（"一个在 XX 上基于 YY 的用于 ZZ 的 WW" 式三层定语链）？
- 段落之间过渡是否自然？段落内信息递进是否被插入语打断？

### 滤网二：黑话与口语

对照 CLAUDE.md 的两份清单逐行扫描：

**禁词表**（正文与标题一律不用）：
颠覆、革命性、炸裂、王炸、吊打、秒杀、遥遥领先、天花板、终极、震撼、必看、干货、硬核（作形容词）、赋能、抓手、闭环（作动词）、完美、极致。

**退役标签**（改用通用术语）：
三堵墙 → 三类物理约束（内存容量/内存带宽/功耗与异构）；一个 token 的一生 → 推理流水线；心跳 → decode step；凿墙 → 优化；眼镜 → Roofline 模型/分析框架；脊柱 → 主线。

**常见口语/俏皮/比喻**（改为准确严肃的技术语言）：
挤牙膏/白赚/攥在手里/这副眼镜/吐字/伺候/刷满整屏/变笨了/不吃饭不睡觉/冲刺/粗账/听着很多/解剖标本/版图/站在哪/跑不动/拉低/磨掉/兑现诺言/严丝合缝。

**额外比喻检查**：
- "标本"、"解剖"——退役，改为"分析对象""选它来分析"
- "尺子"——可保留一处作为教学比喻，但不过度复用
- "富余/格外奢侈/一箭双雕/同一枚硬币的两面"——改为精确陈述

### 滤网三：严谨

- 是否有"显著/大幅/极大"等未用数字支撑的形容词？
- 是否有把虚浮概念当事实陈述的句子（"具有良好的应用前景""扮演着至关重要的角色"）？
- **断言四级制标签（【实证】【文档】【常识】【推测】）是否暴露给了读者？**——这是写作自检工具，正文和括注中一律不得出现，应改为自然语言交代来源。
- 引言/表注中是否还有过时的"见本章末参考"指向（参考节已删除）？
- 数字是否有歧义（未标明 GiB 计法 / 单位 / 条件）？
- 是否在正文中连续出现多个"换句话说"？

### 滤网四：叙事姿态

这类问题不是措辞层面的"不严谨"，而是一种**把技术书写成口头讲解稿**的倾向。逐段检查以下六种模式：

**拟人化**——给软件、数据、代码赋予人的行为或生物的动作：
- `token id 躺在门口` / `模型一口吞进` / `跟泄漏检查器打架` / `模型只吃数字` / `不用你操心`
- 修正：还原为精确的动作描述。数据不会"躺"，程序不会"吞"，检查器不会"打架"。

**竞技/对抗隐喻**——把技术约束描述为比赛或战斗：
- `拼算力 / 拼带宽 / 堆算力 / 干等内存 / 被带宽顶住`
- 修正：用"受...约束"代替动词。`prefill 受计算能力约束，decode 受内存带宽约束`。

**民间智慧式总结**——用口号/谚语代替精确陈述：
- `接着已有的往下补，别从头来` / `已经算过的，别再算第二遍`
- 修正：拆成精确陈述——在哪一层、续写什么、取代了什么。

**叙事性预告**——作者在"导演"读者的认知节奏：
- `此刻看着奇怪、到第 10 章会豁然` / `这里先埋个伏笔`
- 修正：平实交代即可。`此刻看似特殊、在第 10 章会变得清晰`。

**文学化修饰**——借文艺词汇增色，反而减分：
- `鸟瞰`（章节标题）/ `耐人寻味` / `薄得几乎透明`
- 修正：用功能性表述替换，或直接删掉。章节标题不是书名，不承载信息量的形容词一律去掉。

**文化特定指代**——假设读者共享同一语境：
- `不是 PPT 上的方框` → `不是抽象的概念划分`
- 修正：换成普遍可理解的技术描述。

**方言/俚语**——使用了特定圈子或地域的口语：
- `一把梭`（四川麻将术语，意为"一次性全部投入"）
- 修正：用标准书面语替换。`若未配置 chunk size，则不做分块`。

**行业体验行话**——借用了特定产品领域的体验描述词：
- `响应跟手`（移动端 UX 行话，指触控响应延迟低）
- 修正：用通用技术表述。`实时响应`。


### 滤网五：跨文件联动一致性

章标题、术语、结构性改动后，正文之外还有四处会残留旧内容，逐一核对：

- **SUMMARY.md**——章标题改名后这里不会自动跟随，而 HTML 侧边栏/目录用的正是它。
- **scripts/finalize_pdf.py 的 UNITS 表**——PDF 目录页标题与页脚短名来自这里，同样需要手动同步。
- **SVG 的 aria-label 与注释**——无障碍朗读文本是读者可感知的，退役标签要一并改；`grep -o 'aria-label="[^"]*"' chapters/*/figs/*.svg` 可查。
- **尾声/前言等低频修订文件**——正文逐章审校时容易漏掉它们，退役标签和口语（如"解剖标本/拆完了/深坑/富矿/入场/干活"）最后往往藏在这里。

核对命令：逐章 H1 与 SUMMARY 比对、UNITS 表与 H1 比对，见 ch02 改名事故：正文标题已改，SUMMARY/UNITS/PDF 三处滞留旧名一轮才被发现。

## 修正方法

**结构层**：如果某节内信息递进被插入语/旁注打断，重新排序——核心计算 → 解释 → nuance/修正，nuance 紧贴在它所修正的断言之后，不放到远处。

**表述层**：口语/比喻直接用精确表述替换，不保留"生动性"。教学比喻整章至多保留一处，显式声明其教学用途。

**格式层**：
- 行内数学公式必须写 `\\(...\\)`（不是 `$...$`），块级写 `$$...$$`。mdBook 的 markdown 渲染器会吃掉 `\\(` 中的反斜杠，所以源文件中要写 `\\\\(...\\\\)` 才能得到正确的 `\\(...\\)`。
- 代码引用格式统一为 `file:line`（锚定版本由前言声明），不用 `@ v0.13.1` 后缀。

## 审校之外的观察

如果发现以下跨章问题，报告但不直接改（可能需要单独处理）：
- SVG 图内文字含有退役标签（如"三堵墙"出现在图 1-1 内）
- 附录 D 数据与正文数字对不拢
- 交叉引用指向了错误的章号或已删除的章节

## 每章审校后自检

- [ ] `bash scripts/lint_prose.sh chapters/<slug>/chapter.md` 0 命中
- [ ] `mdbook build` 0 WARN
- [ ] 该章使命句是否短（不超过两句）、具体（给出了读者能获得什么）、说明了本章在全书中的角色？

## 示例

### ch01 审校改动要点

- "先算最直观的一笔账：模型有多大" → 开门交底："一个模型能否装进手机，取决于四项内存开销"
- "刷满整屏/慢了两个数量级" → "返回完整结果/慢了这么多"
- "不是模型变笨了" → "不是模型发生了变化"
- "不吃饭不睡觉不亮屏、把整块电池榨干" → "把整块电池的理想电量全部用于访存的极端上限"
- "一张版图：LiteRT-LM 站在哪" → "同类项目对照"
- "（【文档】级，官方博客，出处见附录 F）" → "（依据 Google 官方博客，出处见附录 F）"
- `$L$` → `\\(L\\)`（源代码中写 `\\\\(L\\\\)`）

### ch02/03 新增问题类型示例

- 拟人化：`token id 躺在门口，模型一口吞进` → `token id 已经就绪，送入模型处理`
- 竞技隐喻：`prefill 拼算力，decode 拼带宽；堆算力就快` → `prefill 受计算能力约束；增加算力即可提速`
- 民间智慧：`接着已有的往下补，别从头来` → `在前面已有内容基础上续写而非从头计算`
- 叙事预告：`此刻看着奇怪、到第 10 章会豁然` → `此刻看似特殊、在第 10 章会变得清晰`
- 文学修饰：`跑起来与鸟瞰`（章标题）→ `从运行到架构`；`不是 PPT 上的方框` → `不是抽象的概念划分`
