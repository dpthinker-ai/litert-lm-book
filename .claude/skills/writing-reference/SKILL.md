# 行文逻辑与文笔手法参考库

## 来源与使用原则

两本参照书（引用简称与页码指其 PDF 版）：

- **《工程》**：《推理工程》（Inference Engineering），Philip Kiely 著，Baseten 出版，143 页。从业者叙事体：问题驱动、决策导向、当面算账。强项是章节骨架与讲解装置。
- **《手册》**：《LLM 推理手册》（LLM Inference Handbook），Modular 出品，220 页。问答体参考书：定义先行、每节自足、收益必配反向提醒。强项是概念推导链与"何时不用"纪律。

使用原则一句话：**结构与逻辑照单学，中文表层按 CLAUDE.md 过滤重写**。两本都是译本，均有翻译腔与文档声口（高频"你"、bullet 密度、套语），这些不学（见「过滤器」节）。两本的深度都止于"机制 + 决策"，没有代码层——代码级证据链（`file:line` 锚定、逐行核验）是本书拉开差距的维度，参照书没有可学对象，按 CLAUDE.md 第二节执行。

## 一、章节与节的骨架

### 1. 优化技术的标准骨架（七拍）

两本书讲每项优化技术的共同模板：
①一句定义，常先钉死承诺边界（《手册》投机解码开篇即"输出与 target 单独生成完全一致"）→ ②为什么需要（现状机制 → 痛点）→ ③如何工作（编号步骤 + 图示实例）→ ④量化收益（署名出处 + 条件）→ ⑤代价与失效条件（可独立成节，标题带否定："分离并不总是银弹"）→ ⑥何时用 / 何时不用 → ⑦指路延伸。

骨架的关键不是顺序，而是**成对纪律：每报一个收益，必跟一个反向提醒**。《工程》在技术章开篇就把这个契约告诉读者："请特别关注每种技术推荐使用的场景，以及它引入的潜在瓶颈或权衡"（p71）。

本书对应：第 6-9 章各优化主题按此自查——收益句后有没有紧跟条件句？"何时失效"是否与"为何有效"同段或紧邻？

### 2. 概念引入的因果链：性质是推出来的，不是告知的

《手册》讲 prefill 的三步链（p17）：从"整个 prompt 在计算前已全部可用"这一**事实**，推出可并行这一**性质**，再推出 compute-bound 并挂上 TTFT 这一**指标**；decode 完全对偶。compute-bound 不是被告知的，是被推出来的。写机制时自查：结论前面有没有那个读者可以自己接住的事实？

变体（《工程》p28 激活函数）：先讲问题（matmul 可组合 → 多层塌缩成单层），再给方案（ReLU）——机制动机化，定义永远不裸降。

### 3. 当面算账的完整形（五步）

《工程》算术强度一节（p39-43）与《手册》GPU 内存一节（p56-58）合并出完整形：

1. **先立标尺**：给出对照数字（H100 的 ops:byte 比率 295），读者知道待会儿算出的数要跟谁比；
2. **公式后置**：物理意义讲完才给公式，符号定义带单位与换算理由（"除以 8 是把 bit 转换为 byte"）；
3. **代入演示**：整数玩具值，读者可验算（3350/140≈24 tokens/s）；
4. **结论落地**：算出的数直接推出判断（62 ≪ 295 → decode 受内存限制）；
5. **交代边界**：算完就承认口径（"这种按百分比估算的 Overhead 只是快速 sizing 的捷径，并不是精确的容量模型"《手册》p57；"更像是一种学术练习……但至少亲眼见过一次，对于建立直觉很有帮助"《工程》p43）。

加分手法：**一个算例支撑多个结论**（《手册》p50 的 24 tokens/s 被复用解释 prefill/decode 差异与 batching 为何有效）；**破天真推算**（先替读者把想当然的账算出来再指出错处："7B 模型在 FP16 下仅权重约 14 GB，因此它也许能加载到 16 GB 的 GPU 上。但这并不意味着该 GPU 还有足够余量"《手册》p56——"也许能加载"的让步分寸要学）；**量纲锚点**（推导中途插实物参照："一个 4096×4096 的矩阵大约是 32 MiB，差不多相当于一张高分辨率 RAW 单反照片"《工程》p41）。

### 4. 决策类内容：把参数翻译成约束

《手册》选 GPU 节（p48-55）避免特性罗列的核心手法：让每个技术参数以"它决定你的什么上限"出场——VRAM 决定模型规模与上下文上限、带宽决定 decode 上限、FLOPS 决定 prefill。读者顺着自己的约束走，自然走到候选项。配套动作是教读数能力而非喂结论（"注意星号说明""FLOPS 不是面向用户的指标"）。

本书对应：第 1 章三类约束、第 8 章后端选择，都可按"参数 = 约束"的出场方式自查。

### 5. 同类方案对比的三种组织

- **演进链**（《工程》投机解码族 p76-81）：按"前者的缺陷引出后者"串起 draft-target → Medusa → EAGLE → N-gram，每个变体以适用场景收束，节尾一段横向总揽。适用于有明确演进关系的方案族。
- **统一坐标表 + 条件清单**（《工程》推理引擎 p64-67）：维度对比表前置，逐个分述，各以"在以下情况下，你应当使用 X"收尾，**全程不下全局裁决**；笔墨随结论分配（并行三方式中 PP 不展开）。这与本书「对照视野」的"不下裁决"规则同路，可作侧栏范式。
- **换轴**（《手册》serverless vs self-hosted p36-38）：把"谁好"改写成"什么阶段/什么画像该用谁"，开篇定调光谱而非二元（"生产部署实际上可以落在这两者之间的任意位置"）。适用清单后必给反向出口（"否则，混合部署……可能是开销更低的更优选择"）。

补充：**分类学后置**（《手册》投机解码 p139）——先讲透经典形态，再给变体分类树；开局摆分类树是教科书常见病。**同图式画法**（《手册》并行五策略 p162-165）：多个方案共用一套视觉语言，差异靠并排看图自现。

### 6. 全景图先行

《手册》GPU 架构节（p173-175）：一张大图画出 thread→warp→block→SM→L2→HBM 嵌套关系，**术语全部在图内首次出现且带锚定数字**（L2 50 MB、HBM 3.35 TB/s、延迟 400+ 周期），正文随后才逐个立定义——读者带着地图进正文。本书第 2 章五层架构图已是此路，新增结构性内容时沿用。

### 7. 工程实践内容：通用方案 → 约束否定 → 替代

《工程》生产环境章（p119-125）避开操作手册味的骨架：先介绍通用方案（蓝绿部署），随即用本领域约束否定它（"如果蓝色部署占用了 100 块 GPU，那么在流量切换前，绿色部署也需要再准备 100 块 GPU"），于是引出替代（金丝雀），陷阱与经济账是正文而非附注。"怎么做"只占一格，"为什么换方案"占大头。本书第 7 章发布与回滚、尾声部署诊断适用。

## 二、开篇、过渡与收尾

### 开篇式样（第一句就交付信息，零热身）

- **定义断言，单句成段**："GPU 是吞吐量机器。"（《工程》p45）
- **已知锚点**："如果你熟悉 CPU，你大概听说过核心。"（《工程》p46）
- **问题先行**："在同一份数据上背靠背运行两个不同的 kernel，会导致不必要的内存读写浪费。"（《工程》p60）
- **矛盾并置**："KV 缓存非常宝贵。但 KV 缓存会占用大量内存，而 GPU 的 VRAM 是有限的。"（《工程》p83）
- **读者处境转变**："从使用公共 API 的 token 消费模式，切换到在专用 GPU 上自己做推理，意味着你必须改变对成本的理解方式。"（《工程》p121）
- **定义即纠偏**：第二句就纠正最常见误解并划清边界——PagedAttention"在服务中的主要收益并不来自更快的注意力内核，而来自服务引擎分配和管理 KV 缓存内存的方式"（《手册》p133）
- **路线图句**（节首定位）："本页将带你走完整条流水线：文本如何变成 token、模型内部的架构是什么样，以及推理如何经过 prefill 和 decode 两个阶段。"（《手册》p15）

### 过渡手法（过渡句自身携带论断，不用"接下来我们看"式纯路标）

- **残余问题接力**："如果完成这些优化后，你仍然需要超过单张 GPU 所能提供的 VRAM……该怎么办？"（《工程》p85）
- **读者疑问铰链**：把读者的下一个疑问说出来——"既然你已经理解了 structured outputs 的重要性，下一个问题就是：到底该如何得到它们？"（《手册》p100）
- **镜像反转**："有时，推理工程师遇到的是相反的问题：GPU 对模型来说太大了。"（《工程》p53）
- **递进否定**："这不是 CUDA 问题，也不是 PyTorch 问题，而是一个必须在基础设施层解决的系统问题。"（《工程》p14）
- **节尾递进下一节**：测试节的结尾就是部署节的引言——"一旦你对更新后推理系统的性能与稳定性有了足够信心，就该部署到生产环境了。"（《工程》p120）
- **兜底过渡**（打消顾虑同时转场）："如果你处理的是高度敏感领域……不用担心：本章中的其他所有技术在质量上都是无损的。"（《工程》p76）

### 收尾式样（禁复述式总结，落在下列之一）

- **决策规则**："只有在存在明确且迫切的业务需求时，才应切换。"（《工程》p18）
- **诊断规则**："当推理时间很快、但端到端时间很慢时，你应该把注意力转向基础设施，而不是模型性能优化。"（《工程》p25）
- **失败后果**："否则，在自动扩缩容完成前，请求会排队，用户将看到延迟尖峰。"（《工程》p121）
- **决策函数**（只列自变量，不下普适裁决）："这个决策通常取决于合规要求、流量模式，以及你的团队愿意承担多少运维复杂度。"（《手册》p70）
- **重新定性**："它应当被视为工作负载特定的调度参数，而不是一个通用常数。"（《手册》p131）
- **表象与机制对照**："尽管输出看起来几乎是即时出现的，但在 decode 过程中，这一过程实际上是一次一个 token 地运行。"（《手册》p22）
- **具体例子收尾，不加总结**（《工程》p54 以 Orpheus TTS 用 MIG 实例的例子直接收束）

## 三、讲解装置

### 定义与边界

- **定义句公式**：术语 +"是/指的是"+ 上位概念 + 功能限定，一句完成，**动机单独成段**——定义句可被逐字引用而不失真（《手册》全书）。
- **边界句**：定义后立刻说"此技术不管什么"——投机解码"只改善 TPS/ITL，不改善 TTFT"（《工程》p76）；"它们不会改变模型权重"（《手册》p113 讲推理参数的第二句）。
- **负空间定义**：先排除读者已知的东西再定位——"kernel 优化不是 batching/caching；kernel 优化＝单个操作多快，系统优化＝请求流动多高效"（《手册》p170）。
- **症状式定义**："'长上下文'其实有点同义反复：当一个序列生成的 KV 缓存大到足以在推理中引发问题时，它就成了'长上下文'。"（《工程》p85）

### 纠偏与升级

- **命名天真做法再升级**："一种天真的做法是只看平均值……然而，这并不能说明全部情况。"→ 右偏分布 → 百分位（《工程》p24）。
- **误解纠正**："严格来说，LLM 并没有真正的'记忆'。"（《手册》p20）；"较小的模型通常并不是从较大的模型蒸馏而来。相反，这些模型通常是独立训练的。"（《工程》p22）
- **预判读者直觉并当面拆**："50,000 小时听起来很长，但如果一个包含 8 块 GPU 的单节点全年都用于推理，那就是超过 70,000 GPU 小时。"（《工程》p118）
- **候选方案逐一审判**：每个候选给机制级否决理由，胜出者仍附使用前提（《手册》p206 对 CPU util/GPU util/QPS/concurrency 的审判，如"nvml 在采样窗口内跑过任意 kernel 即记 utilized"）。
- **纠偏→证据→原则三句闭合**："不一定。命中一个负载过高 worker 上的缓存，可能比命中一个轻载 worker 上较小的缓存更慢。好的路由器会把缓存重叠和队列、容量信号结合起来。"（《手册》p156）

### 类比纪律（与 CLAUDE.md"类比要收敛"配合）

- **三步法：类比 → 映射 → 技术复述**，用完即收。范本：数独——"解出数独很难，但检查答案是否正确却很容易。对于目标模型来说，生成一个 token 就像解数独，而验证一个草稿 token 就像检查已经完成的数独"（《工程》p77），只映射"生成/验证不对称"这一个点。冰箱三明治类比后立即给映射与量级（《手册》p172）。
- **拆类比比用类比更透**：先立读者直觉里的词（"记忆"），当场拆掉，机制随拆随出（《手册》p20）。
- **零成本直觉：用正在发生的行为当证据**——讲滑动窗口注意力："我此刻写下的这句话，与上一句话密切相关，但与本章开头几句话的关系就没那么强。"（《工程》p44）
- **机制照亮读者见过的现象**：解释 API 计价页 cache hit 便宜于 cache miss 的原因（《工程》p82）。本书对应素材：Android 上模型加载变慢与 mmap、benchmark 输出里的字段。

### 精确化与辨析

- **术语精确化**：指出通用词的多义（TPS 既可以是延迟指标也可以是吞吐指标）→ 给更具体的替代（感知 TPS/总 TPS/ITL）（《工程》p23）。
- **对比句收拢**："基准测试告诉你系统表现如何；剖析告诉你它为什么会这样表现。"（《工程》p69）——对仗落在实义上，不是空金句。
- **概念辨析对**："路由器回答的是'这个请求应该去哪里？'……负载均衡器回答的是'这个请求可以去哪里？'"（《工程》p115）
- **权衡对句**（对称结构写两侧代价）："粒度越细，抹平离群值的概率越低，也就越能保留质量。不过，粒度越细，存储和应用缩放因子的开销也越大。"（《工程》p73）；固定 γ"GPU 有空余能力时可能过于保守；系统繁忙时又可能过于激进"（《手册》p142）——两侧失败模式写全，下一步的必要性不宣自明。
- **"工具而非目标"句式**："Occupancy 是一种隐藏 latency 的工具，而不是一个应该盲目最大化的性能指标。先 profile，再判断。"（《手册》p176）可移植到一切易被盲目最大化的参数（prefill_chunk_size、上下文长度、量化位宽）。
- **先立后限节奏**：肯定陈述后紧跟"不过，"补边界——《手册》全书十余次的签名节奏，与"每报收益必跟反向提醒"同源。

### 其他

- **命名拆解**：把真实标识符当教具逐段解开（《工程》p32 把 `Qwen3MoeForCausalLM` 解成家族/版本/MoE/因果 LM）。本书直接适用：signature 名、`.litertlm` section 名、类名。
- **立靶在先，论断在后**：先摆两段对照材料让读者自己看出差别，再下结论（《手册》p99 纯文本回复 vs JSON）。
- **经验法则写法**：显式自报身份（"一个经验法则是："）；本体是可执行判断句（不等式或带动词指令）；出现在机理讲完之后，是机理的压缩而非替代（《手册》p55 CUDA 版本不等式；《工程》p78 草稿模型"至少小十倍"）。本书须叠加出处纪律：经验法则要么可溯源（脚注），要么标【推测】改写为"我们推测"。
- **原则复调**：一条核心纪律在全书关键处重复出现（《工程》"约束越多、性能越好"两章两现；《手册》"先在你自己的负载上做基准"四现）——但措辞每次变化，不逐字复读。本书的候选复调：一切性能数字带条件；与代码冲突时改书不改事实。
- **按阶段给相反建议**：早期产品用 API，"但当进入扩展阶段时，建议则正好相反"（《工程》p20）。

## 四、数字纪律（在 CLAUDE.md 数字纪律之上的句法补充）

- **收益句五件套**：报告者显名 + 对比基线 + 条件 + "最高/约"限定 + 反向提醒。"原始的 PagedAttention 论文报告称……只有 20.4%-38.2% 被用于存储真实 token 状态"（《手册》p134）；速度与质量代价同报（"最多可提升 1.46× 速度，同时把准确率下降限制在 1.8% 以内"p143）。
- **先破线性期待再给区间**："从 16 位降到 8 位并不会线性地快两倍。实际中……通常能带来 30% 到 50% 的性能提升。"（《工程》p72）
- **区间不给假精度，约数有标记**：SSD ~1-10 GB/s；"约为……7 倍"（《手册》）。
- **表后算结论句**：数据表后加一句读者可验算的判断——"最便宜区域与最贵区域之间的差距接近 60%"（《手册》p216）。
- **无实测处显式假设算账**："如果每个阶段耗时 50 ms，那么四个阶段……累积出数百毫秒。"（《手册》p209）本书对应：NPU 等"基于代码分析"部分可用此式，假设值显式标出。
- **数字推出决策**：TLS 握手占 300 ms SLA 的"至少 10% 延迟预算"→ 复用会话（《工程》p124）——把开销翻译成预算占比，数字逼出行动。
- **统计翻译成体验**：P90 说成"每十次里就有一次要花上好几秒，体验仍然不好"（《工程》p24）。
- **数字素养：教读者防造假**：短 prompt、大 batch 如何让 TPS 虚高（《手册》p31）。本书第 2 章 benchmark 解读的现成路数。
- **易变事实盖时间戳**："在本书出版时"（《工程》多处）；主观指标先自贬口径（"GitHub star 数量只能粗略反映受欢迎程度"）。

## 五、图表分工（在 CLAUDE.md 图表规范之上的补充）

- **分工律**：嵌套/空间结构才配图；A vs B 权衡用表；线性数据流用箭头文字串（`Query → Embed → Rerank → Generate`）不必开图。

- **指标画成时间轴线段**：同一张流水线图画两遍，分别括出 TTFT 与 E2EL/ITL 覆盖段（《手册》p29）——指标定义与图互相印证。

## 六、全书级装置

- **口径声明一次说清**："除非另有说明，本手册中的 'LLM' 都指 decoder-only Transformer 模型。"（《手册》p21）本书已有对应（前言声明 v0.13.1 与单位口径），新口径出现时沿用此式。
- **术语表条目结构**（《工程》附录 A）：中文术语（English，缩写）+ 第一句定义 + 第二句意义/权衡/量级，2 句为主；同名多义括号消歧；同义词条目只写"见 X"；范本："KV 缓存……用于避免重复计算注意力，从而将注意力方程从二次时间操作转变为线性时间操作。"
- **利益相关隔离**：厂商内容集中末节、标题点名、首句坦白视角（《工程》7.6）。本书对应：非官方身份声明已在前言；"基于代码分析、无实测"的标注属同一诚实纪律。
- **知识截止声明**："和 LLM 一样，书也有知识截止日期。本书于 2026 年 1 月完稿。"（《工程》p16）——把时效性写成事实而非道歉。
- **受众分流开篇**："有些系统追求的是吞吐量，而不是延迟。"（《工程》p124）——一句话让不相关读者知道可以跳过。

## 七、过滤器：不学清单与冲突裁决

两本书的以下形态**不学**（多为译本通病或网页文档声口）：

1. 中英夹杂断裂句（"Knowledge distillation is a model 压缩技术"）；英文残句未删。
2. 名词化与轻动词直译（"识别出最佳解决方案""对它们的输出进行合并"）；"人们已经开发出"式被动腔；help X by Y-ing 嵌套。
3. 硬译词："姿态"（posture）、"既是祝福也是诅咒"、"令人印象深刻"、"讲述性能故事"、"保持正确轨道"、"发挥作用的地方"（This is where X comes in）、"表面上看，这似乎很直接"。
4. 套语复用成癖："放之四海而皆准"三现、"银弹"、"幸运的是"句首填充、"本质上"。
5. 陈腐类比："核心大脑""高性能跑车"；失准类比（书页讲 PagedAttention 丢掉 OS 分页对应）。
6. 无出处经验数字；营销数字（"最多低 6 倍"无条件）；厂商软广混入正文。
7. bullet 依赖症与"**加粗词**：解释"四连骨架；FAQ 复读正文。
8. 语域失当："奇技淫巧""榨干""魔法真正发生的地方"；竞技隐喻"押注……获胜"。

与 CLAUDE.md 的冲突裁决（一律 CLAUDE.md 胜）：

| 参照书手法 | 本书裁决 |
|---|---|
| 高频"你"直呼读者 | 维持现状：省主语与"读者"为主；"你"不成为默认人称 |
| bullet 密度（每节多处） | 列表节制：每节至多 1 处，真并列才用；参照书的"列表前必有引导句"照学 |
| 单句成段高频 | 只用于转折与强调处，服从段落长短节奏自查 |
| 设问过渡高频 | 少量使用，不成套路（除 AI 味第 18 条）；设问式小标题不引入 |
| 幽默配额（正文打趣） | 不引入正文；语气纪律优先 |
| "不是 X 而是 Y"句式 | 有效但限量（humanizer 第 17 条忌当口头禅）；关键纠偏处才用 |
| 经验数字不注出处 | 断言四级制：可溯源加脚注，否则标"我们推测"或删 |
| FAQ 章末小节 | 不引入；易混概念辨析写进正文或练习 |
| 交互组件承担讲解 | 不适用；由 SVG 图 + 当面算账承担 |

## 八、落笔检查单（写或改一节时过一遍)

1. 第一句是否交付信息（定义/矛盾/问题/处境），有无热身空转？
2. 新概念：定义句能否被逐字引用？动机是否另起？定义后有没有边界句（"它不管什么"）？
3. 机制的性质（memory-bound、可并行……）是推出来的还是告知的？
4. 每个收益句后面，条件与失效场景在不在同段或紧邻？
5. 有账可算的地方：标尺先立了吗？读者能验算吗？算完交代口径边界了吗？能否加一个破天真推算或量纲锚点？
6. 同类方案对比：选了哪种组织（演进链/坐标表+条件清单/换轴）？收尾是不是决策函数而非裁决？
7. 类比是否走完"类比→映射→复述"三步并及时收掉？有没有可用"拆类比"替代的地方？
8. 过渡句自身有论断吗？还是纯路标？
9. 节尾落在哪：决策规则/诊断规则/失败后果/重新定性？有没有复述式总结混进来？
10. 过滤器扫一遍：翻译腔、套语、bullet 骨架、无出处数字。

检查单跑完后，语言层再交 book-review skill（禁词表、退役标签、叙事姿态）与 `scripts/lint_prose.sh`。
