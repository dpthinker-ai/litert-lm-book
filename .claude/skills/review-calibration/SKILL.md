# 审校校准：问题类型学与修法库

来历：2026-08-29 作者经 Artifact 评论逐条批注前言与第 1 章（54 条批注加 20 余轮追加讨论），全部修复后沉淀。与 CLAUDE.md 冲突处以 CLAUDE.md 为准；本文件是其实战细化。所举实例均出自第 1 章定稿，可对照阅读。

## 一、协作规范（作者裁定，硬性）

1. **统领全局，不对单条批注言听计从。** 批注表达的是"这里有问题"，不总是"按字面改"。先诊断为什么别扭、看它在全章结构中的位置，再决定改法；与全局冲突时给出理由与替代方案。实例：作者建议删"单项能耗"半句，照删后破坏了与三类约束的对应——正解是给第三项换谓语（部分与整体关系不硬套"X 不等于 Y"排比），不是删除。
2. **可以有理有据地不照改。** "设→假设"一条最终保留"设"：定义符号（设/记为）与假设取值（假定）是两种动作，照改会把定义误标成命题；但作者的语感指出了真问题——全节两类动作用词混同，于是把 50 GB/s 处的"设为"改成"假定为"。回复时先给结论再给理由。
3. **连续几版都别扭的句子，先找病根再动笔。** 换词救不了结构病：过渡靠序数词硬顶、部分-整体硬套排比、预告悬空无所指，都是换十次措辞也治不好的。
4. **错删认账。** 误解批注锚点或改错位置，按原文恢复并说明（"可以"一词曾删错句子）。
5. **同类扫尾。** 一处发现的问题 grep 全书扫同类：引号「」、int4 大小写、预留长度/宽度混用、"Roofline 记号"都在别章有同伙。
6. **术语存疑先查业界，不凭语感裁决。** payload 与"容量"两案均经检索后定案；查证结论要带来源回给作者。

## 二、问题类型学（审校时逐类过筛）

### A. 术语

- **A1 自造术语与生造搭配**：业界无专名的量不造词，用"业界名词＋口径限定词"表达。案例链：权重 payload→本体→有效载荷→最终"权重大小（理想值）"；逻辑容量→理论容量→最终"KV cache 理论大小"；"Roofline 记号"→"Roofline 模型"。自查法：这个复合词在业界文献里搜得到吗？搜不到就拆成平实说法。
- **A2 首现无定义**：每个承重名词首次出现处要么定义要么括注（今天补掉的：后端、工作点、稠密、GQA、FFN、预留宽度、缓冲策略、TOPS、片上缓存、虚拟映射、RSS、后端工作区、外部权重、目标后端、批内、pJ）。高频词连打括注补丁不如一次正面定义——"后端"先后打了四个补丁，最终在 1.1 节正面定义一次全部解决。
- **A3 同义混用**：模型进程/推理进程、预留长度/预留宽度、绑核/核心绑定、delegate/后端委托、带宽约束区/受带宽约束——全书一词一物，首现定哪个后文跟哪个。
- **A4 体例统一**：数据格式名正文大写（INT4/INT8/FP16/FP32），代码、文件名、终端实录保持原样；引号用“”不用「」。
- **A5 行话压缩与语域偏移**："批内"→"这一批里的所有请求"；公文腔（"可行范围"）与口语同属语域偏移，双向排查。

### B. 句段连贯

- **B1 孤句拼盘**：一段里三五个短句各自为政即嫌疑（"两个阶段的计算特征不同。"九字孤句是反例）；合并为分号平行或因果衔接的完整句，定义、对比、限定各占一句。
- **B2 过渡失效**：靠序数词（"第二笔大账"）或空话头（"取决于执行方式"）硬转。修法：过渡句自身携带论断——"权重的理想值算一次就不再变。KV cache 不同，它随上下文增长，足够长时甚至会超过权重。"
- **B3 缺回环**：推理链推出去不收回段首论点。修法：末句显式收口（mmap 段以"步步如此，工作集就接近全部权重"收回"映射省不掉工作集"）。
- **B4 指代悬空**：前者、前两项、这项前提、后一条路径——一律写实名。
- **B5 罗列无目的**：一串假设或因素并排而不说共同目的。修法：目的先行＋逐条带理由＋"否则…"收口（题设段：所有假设为了让带宽成为唯一瓶颈，"否则上限就不由带宽决定"）。

### C. 逻辑与事实

- **C1 必然写成条件**："若权重远大于片上缓存"——GiB 对 MiB 是三个数量级的必然，直陈并给量级；例外（MoE、权重常驻片上缓存）由下一句显式承担，不靠"若"字留门。
- **C2 连接词错标关系**：代入不是因果（"因此"→"代入后"）；定义不是假设（设/记为＝命名，假定＝取值假设）。
- **C3 归类错误**：影响理论值的因素（层数、GQA、数据类型）与影响实际分配的因素（预留宽度、缓冲策略）不同类，不得同列一张原因清单。
- **C4 以偏概全**：分级事物按合适的一级说话（缓存分级，论证锚在"容量最大的一级也只有几十 MiB"）。
- **C5 悬空预告**：读者尚无所指的前向预告删除，限定句留在其所属章节（1.2 的能耗预告删除，1.5 自带完整限定）。
- **C6 代码事实被质疑就回源码验**：端侧编译经 `cache_compiled_shaders_only` 与程序缓存证实；NPU 预编译例外经第 8 章证实。作者的质疑常有一半是对的——把对的那一半写进正文（1.1 节的三路径编译澄清句即由此来）。

### D. 数字与算账

- **D1 取值有来历**：代入值标出处（D≈2×10⁹ 即权重大小；0.5 GiB 按 1.3 节参数；能耗段流量"仍取 1.4 节的 2×10⁹ 字节"）。
- **D2 忽略有依据**：说可忽略必给比例（写入量 128 KiB 为读取量的 1/4096；短上下文 KV 不到权重的 2%）。
- **D3 上限语义说透**："只会更低，不会更高"。

## 三、修法速查

- **定义登场三式**：负空间定义（"后端不是设备"）；机制自释（"全上下文注意力里，每个新 token 都要与全部已缓存 token 计算注意力"——术语靠自身机制解释）；简称引出（"实际部署所选的后端（下文称目标后端）"）。
- **括注三件套取舍**：英文对照、一句机制、量级锚点，取其一二即可；同段括注堆到四个以上，改为正面定义句。
- **章内债务显式偿还**：前文许诺的账开头点名接上（"1.3 节留下的双缓冲代价，可以在这里交代""现在把先前搁置的 KV cache 加回来"）。
- **前向引用给落点**：不写空指的"见第 N 章"，写"填充从何而来，见第 4 章的固定 signature 分块机制"。
- **对比句平行化**：prefill/decode、服务端/端侧这类对举用一句内分号平行结构，两侧句式对称。

## 四、执行清单（润色一段前后各过一遍）

1. 段内每个承重名词：首现有定义吗？全书同名吗？业界确实这么叫吗？
2. 句间：过渡带论断吗？指代落实了吗？有孤句拼盘吗？段尾收回段首了吗？
3. 逻辑：条件句是真条件吗？连接词与实际关系相符吗？同一清单里的项同类吗？
4. 数字：取值有出处吗？"可忽略"有比例吗？上限的单向性说透了吗？
