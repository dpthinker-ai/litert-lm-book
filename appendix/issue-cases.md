# 附录 H · 上游 issue 案例集

> 全书引用过的 7 个真实 GitHub issue，集中立档。每个 issue 都是运行时某条约束在野外的显形：先记现象（上游报告口径），再指书中的机制解释，最后给一条「你遇到类似问题时」的定位思路。issue 反映的是写作时（v0.13.1）的上游状态，可能已被后续版本修复；链接见附录 F。

## `LiteRT-LM#2568` · `--max-num-tokens` 为什么影响 decode 速度

- **现象**：只改 `--max-num-tokens`，prompt 没变，decode 速度却变了。
- **机制**：该参数决定 KV cache 的预留槽位数。静态路径上注意力按整个预留宽度计算，mask 只挡逻辑、不免访存，预留越宽每步越慢（第 6 章）。默认值按 prompt 长度以 4096 为粒度阶梯推导（`engine_settings.cc:293-301`）。
- **本书验证**：附录 D 第九节扫描——8192 比 1024 慢约 37%；工单恰好打满预留宽度时 prefill 直接报 `dynamic_update_slice` 越界，过小不是变慢而是失败。
- **定位思路**：decode 莫名变慢时，先查预留宽度是否被默认值推导放得过大；手动调小要留意工单形状与预留宽度的边界。

## `LiteRT-LM#2281` · 换个后端，输出怎么不一样了

- **现象**：同一模型同一 prompt，换后端（如 CPU 换 GPU）输出文本不同。
- **机制**：三条后端是三条计算路径，算子实现、激活精度落点、反量化方式都有细微差别；微差累积进 logits，在分数接近处翻转采样排序，再被自回归放大（第 8 章）。不是 bug，是浮点的本来面貌。
- **定位思路**：对数字要区分「实现错误」与「路径差异」——比较后端行为时先固定种子与采样（温度 0），再谈差异；性能与正确性讨论都必须带「哪个后端」这个前提（附录 D 的数字纪律由此而来）。

## `LiteRT-LM#2227` · PowerVR GPU 上 MTP 反而更慢

- **现象**：在 PowerVR GPU 上开推测解码，decode 不降反升（更慢）。
- **机制**：加速比 ≈ E[产出] ÷ (1 + G·c_draft/c_base)。接受率 α 不够高，或该硬件上 drafter 与 verify 的开销比失衡，加速比就跌破 1（第 9 章的盈亏平衡分析）。本书无此真机，现象按上游报告引用。
- **定位思路**：开推测解码前先在目标硬件上实测；加速依赖「drafter 够便宜 + 猜得够准」两个条件同时成立，官方「约 3 倍」口径来自其特定模型/硬件/负载（本书基准未复现，见附录 D）。

## `LiteRT-LM#2589` / `#2613` · Swift 的 deinit 与「单会话」撞车

- **现象**：Swift 侧销毁一个会话后再建新的，报「已有一个会话」——旧会话其实没被释放。
- **机制**：引擎同时只允许一个会话（#2589），而早期 Swift 绑定把释放只交给 ARC 的 `deinit`，时机不确定：引用未归零，delete 就没被调（第 11 章）。#2613 的解法是给 Swift 加公开 `close()`，对齐 Kotlin 的 `AutoCloseable` 与 Python 的 `__exit__`。
- **定位思路**：带独占语义的资源（单会话、独占句柄）不能依赖语言的自动回收，绑定层必须给调用方一条显式释放路径；遇到「资源没释放」类报错，先查释放时机而非释放有无。

## `LiteRT-LM#2418` · 嵌套 JSON 参数的解析边界

- **现象**：某些模型的工具调用在嵌套 JSON 参数上解析出错。
- **机制**：Tool Use 的解析靠 ANTLR 文法（`AntlrFcParser.g4`），`value` 规则递归定义，文法版本演进中曾在嵌套参数上出现边界问题（第 10 章版本注记）。
- **定位思路**：工具调用解析失败时，先隔离是生成侧（模型没按格式吐）还是解析侧（文法没覆盖）：把模型原始输出落盘比对文法规则，问题立刻减半。

## `LiteRT-LM#2505` · CPU 线程数需要一个开关

- **现象（需求）**：CPU 后端的线程数固定不可调，无法按设备调优。
- **机制**：`CpuConfig::number_of_threads` 默认 4（`llm_executor_settings.h:120`）；上游据此在 C++ 侧加了 `--num_cpu_threads` flag（`shared_flags.cc:74`），覆盖路径在 CPU 专属配置分支（`litert_lm_lib.cc:523`）。线程多了未必更快：decode 是带宽受限，线程超过带宽喂核能力后只涨功耗（第 8 章）。
- **定位思路**：CPU 吞吐调优的顺序是——先绑性能核（亲和性），再调线程数；注意 v0.13.1 的 Python CLI 未暴露该 flag，调参需用 C++ `litert_lm_main`。
