# 附录 E · 练习提示与参考答案

> 逐章对应正文末尾的「练习与自查」。复算题给出完整算式；机制题给出要点，展开论证请回到对应章节；动手题给出预期观察。

## 第 1 章

1. int4 7B 权重 7 × 10⁹ × 0.5 B ≈ 3.26 GiB；8K 上下文 KV（示例参数 128 KiB/token）≈ 1 GiB；加 decode 激活 0.1 GiB 共约 4.4 GiB，可用 7 GiB 装得下。32K 上下文 KV 涨到 4 GiB，总量约 7.4 GiB，贴顶并将触发换页。
2. 带宽 9600 × 10⁶ × 8 B = 76.8 GB/s；int8 4B 权重每 token 读 4 × 10⁹ B；上限 76.8 ÷ 4 ≈ 19 tokens/s。
3. 每 token 读 1 GB 时能耗约 20 pJ/byte × 10⁹ ≈ 0.02 J/token；15 Wh = 54000 J，仅访存一项可支撑约 2.7 × 10⁶ token（数量级估算，未计算力与其它系统开销）。
4. prefill 的算术强度高（一批 token 复用同一批权重），落在算力受限区；decode 算术强度低（读全部权重只算一个 token），落在带宽受限区。
5. 不行。decode 受内存带宽约束，算力翻倍不改变每 token 要搬的字节数与搬运速度；要提吞吐，须换更高带宽或减小每 token 字节量（量化、推测解码）。

## 第 2 章

1. 1024 ÷ 999.1 + 1 ÷ 50.6 ≈ 1.025 + 0.020 = 1.045 s，与实测 1.04 s 一致（差异在计时粒度内）。
2. 有效带宽 50.6 × 2.26 ≈ 114 GB/s；4096 档每步 114 ÷ 45.6 ≈ 2.51 GB，比权重多约 0.25 GB，除以 4096 ≈ 60 KiB/token。高于 28 KiB 的原因：恒定带宽假设把注意力计算随上下文增长的耗时也折算成了"字节"。
3. Init 1.8 s 属 GPU 缓存已热的正常量级（附录 D 为 1.77 s）；TTFT 4.4 s 需先看上下文长度，若约 4096 则与 gpu 档实测吻合、属 prefill 的正常账；decode 45 tok/s 与上下文加倍降 8% 均在基准区间内。四项均无异常，不必调优。
4. 否则计时终点落在异步提交返回处，测得的是提交耗时而非硬件完成耗时。实现是 `params.SetWaitForCompletion(wait_for_completion | benchmark_info.has_value())`（`runtime/core/tasks.cc:435`）。
5. `MaskLogits` 在第 4 层（组件层）实现、被第 2 层（编排层）的 `DecodeAndSample` 外部路径调用；它修改的 logits 来自第 3 层执行器的 `DecodeLogits`。

## 第 3 章

1. 任何在渲染末尾追加固定收尾标记（如 `<end_of_turn>` 之后再补一个总结符）的模板：追加新消息时收尾标记位置改变，新串不再以旧串为前缀。前缀检查 `new_string.substr(0, old_string.size()) != old_string` 拦截并返回 `InternalError`。
2. Clone 复用的是已算好的 KV cache（跨会话），代价是一次深拷贝（4096 上下文约 117 MB）；diff 复用的是同一会话的历史 KV，代价是每轮把旧串、新串各渲染一遍（字符串开销，远小于 prefill）。
3. 长度检查拦「新渲染反而变短」（收尾标记被挪走一类）；前缀检查拦「等长或更长但前部被改写」（历史消息被模板重排一类）。
4. 其一，嵌入表是量化的，取数须伴随解量化，编译成子图后两步合并为算子；其二，与主模型解耦后，多模态编码器可以独立产出同空间的 embedding 接入。
5. 例如模板里有字符串字面量 `"call .startswith(x) manually"`：正则按文本匹配 `\.startswith\(...\)`，会把说明文字改写成 ` is startingwith x`，语义被破坏。

## 第 4 章

1. 700 < 1024，铺满循环不执行；收尾从大到小找「再小一档装不下」的入口：128 < 700，故用 1024。工单 [1024]，填充 324，填充率约 32%。若允许 6 个 128 拼接（768 ≥ 700），浪费降到 68（约 9%），这正是源码 TODO 想探索的方向。
2. 激活峰值从正比于 2048 降为正比于 512（约四分之一）；TTFT 略增，因为四段串行执行引入了段间开销。方向：内存换时延。
3. 前面的段提交后必然还有后续工单要排，无需等待即可继续提交，硬件流水不中断；只有最后一段之后没有工作了，调用方若要求完成语义才需要等它落地。
4. 100 token 喂不满向量单元，权重读取占比高，接近带宽受限；token 增多后同一批权重摊到更多计算上，算术强度爬升，直到 261 tok/s 的算力顶。
5. prefill 是一次（或数次分块）大前向，提交后无法从中间打断，取消只能落在块边界；decode 天然逐步循环，每步开头都有一次取消检查。

## 第 5 章

1. 262144 × 2 B = 512 KiB；相对 1.4 GiB 约 0.35‰，比 fp32 再减半，仍可忽略。
2. 不停。`ShouldStop` 第一分支要求 `hit_stop_tokens && benchmark_decode_token_count == 0`，benchmark 模式下该条件为假，循环继续跑满 128 步——这是测量语义优先于生成语义的设计。
3. 产出 A：暂存（可能是停止序列前缀），无输出；产出 B：继续暂存，无输出；产出 C：匹配失败，暂存整段释放，用户一次性收到 ABC。
4. 因为一个字符可能横跨多个 token（UTF-8 多字节序列被切开）。单 token 转换会产出非法字节序列；「暂存 + 新 token」整体转换让 tokenizer 在凑齐完整字符后才输出。

## 第 6 章

1. 28 KiB × 8192 = 224 MiB；静态槽位 32003 全预留 = 28672 B × 32003 ≈ 918 MB。
2. Clone 拷贝 4096 × 28 KiB ≈ 117 MB（`CloneKVCacheBuffers` 逐块 `CopyTensorBuffer`）；Rewind 只把 `current_step` 游标改回检查点值，KV 数据原地留用。一个搬字节，一个改整数。
3. 数据不动、指针换向：读旧写新之后 `std::swap(input_kv_cache_buffers_, output_kv_cache_buffers_)`；prefill 路径在 `llm_litert_compiled_model_executor.cc:738`、decode 路径在 `:947`。
4. 内存：预留缓冲随之翻倍（int8 下每 token 28 KiB）。速度：固定形状路径上注意力按预留长度计算，mask 屏蔽的位置也参与读写，decode 变慢——预留多大，每步为多大付账。
5. 本书基准模型：权重 int4、激活 fp16（GPU 默认）、KV int8。另一合法组合如：权重 int8、激活 fp32、KV fp16——三者各自独立可选。

## 第 7 章

1. `alignment_gap = 49152 mod 65536 = 49152`，`aligned_begin_offset = 0`：从文件头开始映射，返回给上层的指针前移 49152 字节指向段数据。
2. 增量参数 r × (d_in + d_out) = 16 × 5120 = 81920；fp16 占 160 KiB。一个矩阵不到权重全量（2560² × 0.5 B ≈ 3.1 MiB，int4）的 5%。
3. mmap 只登记页表映射，虚拟地址空间立即 +3.66 GB；物理页在首次访问时缺页载入，故 RSS 只包含被访问过的工作集。内存紧张时这些文件后备页可被直接丢弃（不写交换区），下次访问再从文件读回。
4. 多做一步解析：调 `ReadLlmMetadataFromSection` 把段内容读成 proto 并以 `DebugString` 展开打印。只对它多做，因为其他段（权重、tokenizer）是二进制大块，打印原文没有信息量。
5. `LoadLoRA` 只占主存（mmap 读入 LoraData 只读视图）；`UseLoRA` 才建后端资源、占显存。多份 LoRA 可同时驻留主存待命，切换只需为新激活者付第二拍，不重新读盘。

## 第 8 章

1. 省的主要不是字节而是每步一次的「GPU 到 CPU 的同步点」：回搬要求 GPU 流水停下等待传输完成、CPU 参与采样后再发起下一步。片上采样让 decode 循环整体留在设备侧，省掉的是往返延迟与流水线气泡。
2. 其一，重活分给慢核会拖长关键路径（木桶效应）；其二，小核吃满更易触发整机发热降频，反噬大核频率。
3. 防住配置错误在深处爆炸：非法后端在唯一入口处换来一个可读的错误，而不是在某次张量分配时崩溃且难以归因。
4. 浮点运算在不同硬件路径上的舍入次序不同，logits 有微小差异；自回归把微差沿序列放大，几十步后可能选出不同 token。不是 bug，是浮点算术的固有性质（`LiteRT-LM#2281` 即此类报告）。
5. 至少：`Backend` 枚举加值（`executor_settings_base.h`）；`GetBackendFromString` 的解析表；执行器工厂的 `switch` 分支与对应执行器实现；若有专属采样或亲和性逻辑，再加各自的分派点。

## 第 9 章

1. 一轮成本 ≈ 1.3 个 base 前向，期望产出 1 + p + p² + p³。令其等于 1.3，解得 p ≈ 0.24（0.24 + 0.24² + 0.24³ ≈ 0.31）。接受率低于约四分之一时，这套机制开始亏。
2. verify 对 G+1 个位置都给出正确答案：即使首个草拟就错，也能收下位置 0 的 bonus token——一次 base 前向至少换一个 token，与普通 decode 打平。
3. verify signature 的 `input_pos` 维度是编译期固定的形状，G = 该维度 − 1（`llm_litert_mtp_drafter.cc:256`）。改 G 意味着重新导出模型。
4. 推测：benchmark 的合成负载没有真实语言的可预测结构，drafter 接受率低，收益被 drafter 开销抵消。无法实证归因是因为 CLI 不输出接受率计数（它只在析构日志里打印）。
5. 前半是当前 token 的词嵌入（2560 维，来自 embedder 查表），后半是主干上一步的隐藏态 activation（2560 维，来自 decode/verify 的输出缓冲）。

## 第 10 章

1. `target_px = 256 × 256 = 65536`；`factor = √(65536 ÷ 393216) ≈ 0.408`；理想尺寸 313.5 × 209.0；按 `side_mult = 16` 向下对齐得 304 × 208；patch 数 19 × 13 = 247 ≤ 256。
2. 文本无特殊值、视觉 −1、音频 −2。必须为负，因为合法 token id 非负；第 3 章的查表路径对负 id 不查表、填默认向量，正好为占位符留出「先占坑、后覆写」的空间。
3. 每步约 262144 次位读取加条件写，纯顺序内存操作，量级 10⁵。对照每步 10⁹ 字节级的权重搬运，低四个数量级，不构成瓶颈。
4. 编码器：log-mel 频谱分块进、特征出；适配器输入 `features[1, 204, 1536]`（至多 204 帧、1536 维特征），输出对齐主干的 2560 维。拆两级的理由与视觉相同：编码器管特征提取，适配器管投影对齐，后者小得多、可独立替换。
5. 约束解码要在采样前改写 logits。内部采样路径中 logits 不离开执行器（甚至不离开 GPU），上层没有插手的时机；只有外部路径把 logits 交出来，`MaskLogits` 才有落点。

## 第 11 章

1. 好处：C++ 类型完全不出现在 ABI 里，C++ 侧可以任意重构、加虚函数、改布局而不破坏已发布的绑定。代价：跨边界只能传句柄，每个操作都要一次函数调用，无法内联。
2. Swift 对象被闭包或局部变量持有 → `deinit` 不执行 → 桥接层的 delete 不调用 → 原生会话仍占用唯一名额 → 新建会话时运行时判定「已有一个会话」报错。
3. 归 C++ 侧所有（指向内部缓冲或由专门的 free 函数配对释放，视 API 而定）；绑定语言侧擅自 `free` 会破坏另一侧的分配器状态，典型结果是崩溃在无关位置。
4. 停止词、暂存、采样编排全部工作在「token id 序列」这一抽象上，与 id 是谁算出来的无关；脚本化的假执行器给出确定 id 流即可覆盖。它测不了数值层：量化误差、后端差异、真实性能。
5. 创建：`litert_lm_engine_settings_create` 及必要的 set、`litert_lm_engine_create`、`litert_lm_engine_create_session`；使用：`litert_lm_session_run_prefill` / `litert_lm_session_run_decode`（或 conversation 系列）；销毁：`litert_lm_session_delete`、`litert_lm_engine_delete`、settings 的 delete，与创建严格成对。
